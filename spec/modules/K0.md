# K0 Module and Name Resolution

Status: `DRAFT`

1. One source file declares exactly one module path.
2. A package manifest maps a module path to exactly one source file.
3. K0 has no wildcard imports, prelude injection, runtime module initializer, or
   conditional name lookup.
4. Public symbols are keyed by `(package_id, module_path, declared_name)`.
5. Public declarations cannot overload a name by type or arity.
6. Name resolution is completed before type checking and is serialized in ASR as
   a stable symbol identifier.
7. A reference to zero or multiple visible declarations is rejected.
8. Module-level constants are evaluated by the total K0 constant subset. Their
   evaluation order is not observable.
9. K0 has no import declaration. An unqualified symbol path searches only the
   current module. A qualified path maps all components except the final declared
   name to a module path in the same package.
10. Type, value, and contract labels occupy separate namespaces. A nominal type
    and one of its variants may be named in value position; resolution fixes the
    constructor kind before type checking.
11. A lifetime label is scoped to one function signature. Equal spelling in the
    same signature denotes one relation ID; labels do not resolve across items.
12. Allocator brand paths resolve only against the target manifest. Source code
    cannot declare or alias a brand.
13. The package entry resolves through the value namespace to exactly one
    function and is serialized as that function's symbol identity.

The complete experimental algorithm is proposed by LCP-0002 and draft LDR-0006.
Until they are independently reviewed, the rules below are executable evidence,
not an accepted language decision.

## Resolution order

Resolution is a total function over `(spec.lock, package manifest, target,
manifest-named source bytes)`. Module keys are processed in ASCII order. It uses
two passes: declaration/variant collection, followed by signature, contract,
constant, and body resolution. Forward references and recursion do not depend on
source order.

The first rejection is selected by this order:

1. manifest/source closure and module-declaration equality;
2. duplicate declarations, variants, fields, parameters, and contract IDs;
3. symbol-ID collision checks and package-entry existence/kind validation;
4. items by module-path ASCII order and source order, resolving each signature
   before that item's contracts and body.

Children use left-to-right preorder. Parallel completion time cannot select a
diagnostic.

## Path candidate sets

Type, value, contract, lifetime, brand, and local names are disjoint. A lookup
produces a finite candidate set and succeeds only when exactly one candidate of
the required namespace and kind is visible.

- unqualified type: current-module type declaration;
- unqualified value: active local, current-module value, then target host
  primitive;
- qualified value/type: package module prefix plus final declaration;
- enum constructor: current `Type::Variant` or qualified
  `module::Type::Variant`;
- brand: exact `brand:` plus dot-joined path in the target manifest.

If a qualified spelling is simultaneously a module declaration and enum
constructor candidate, the source is rejected as `RESOLVE-AMBIGUOUS`; path length
or source order does not rank candidates. A unique cross-module private candidate
is `RESOLVE-INACCESSIBLE` rather than not found.

## Local and contract scopes

Parameters enter before contracts and the function body. A `let` initializer is
resolved before its binding enters the block. Match bindings exist only in their
arm. Declaring a spelling already active in an enclosing scope is
`RESOLVE-SHADOW`; reuse after that scope ends is allowed.

`result` is reserved for the `ensures` result binding, and target host primitive
spellings are reserved for their locked primitive identities. Module values,
parameters, `let` bindings, and pattern bindings cannot use those spellings.

Invariant scope contains the nominal fields. Function contract scope contains
parameters, and `result` exists only for `ensures`. Contract IDs are unique over
the package and never participate in value lookup.

## Package manifest

The package manifest conforms to `manifests/package.schema.json`. Its module map
is complete: every source file belongs to exactly one declared module, every
declared module has one normalized relative source path, and undeclared source
files cannot enter the package hash. Module paths and normalized paths are
unique. K0 has no dependency list, build script, feature condition, environment
substitution, or generated-source hook.

The manifest `entry` components before the last are joined as the package module
path; the last component is looked up as a function in that module's value
namespace. The ASR stores the resulting symbol ID. Entry lookup does not create
a namespace, visibility exception, overload rule, or source-order fallback.

## Symbol identity

For package ID `P`, module path `M`, namespace `N`, declared name `D`, and item
kind `K`, the stable symbol identity is:

```text
sym:hex16(sha256("aether-k0-symbol\0" || P || "\0" || M || "\0" ||
                 N || "\0" || D || "\0" || K))
```

`hex16` is the first 16 lowercase hexadecimal digits. A hash collision is
`SYMBOL-ID-COLLISION`; implementations must compare the full identity tuple and
must not select one declaration.

Local and lifetime identities use equivalent domain separation:

```text
local:hex16(sha256("aether-k0-local\0" || function_symbol || "\0" ||
                   binder_kind || "\0" || preorder_ordinal || "\0" || name))

life:hex16(sha256("aether-k0-lifetime\0" || function_symbol || "\0" || label))
```

The resolved ASR carries the complete identity tuple next to each short hash.
No implementation may reconstruct binding identity from source spelling alone.

## Constant evaluation

Module constants use `contract_expression`. References form a directed graph.
Resolution rejects cycles with `CONST-CYCLE`, then evaluates nodes in the unique
lexicographic topological order induced by stable symbol identity. Arithmetic is
exact mathematical arithmetic followed by the declared result-type range check.
Evaluation emits no runtime event and cannot read target state except the fixed
width of `usize` and `isize` from the content-addressed target manifest.

# Aether

[![K0 specification](https://github.com/TsekaLuk/aether/actions/workflows/spec.yml/badge.svg)](https://github.com/TsekaLuk/aether/actions/workflows/spec.yml)

Aether is an AI-native trustworthy systems-language research project. Its premise
is that future code will primarily be generated by machines, while people define
intent, responsibility boundaries, and audit requirements.

This repository currently contains the product requirements, the first executable
K0 specification package, independent source parsers, package name resolvers, and
semantic transition executors, a locked proof-assistant path, and an
evidence-backed implementation gate. It does **not** contain a production
compiler and does not claim end-to-end verification.

## Current status

- Specification version: `0.4.0-draft`
- Core layer: `K0`
- G0 implementation gate: **FAIL**
- Authorized work: specification engineering and disposable semantic probes
- Production compiler: **No-Go**

The current executable subset covers move state, borrow conflicts, allocator
brands, allocation failure, explicit deallocation, double-deallocation rejection,
and affine leak diagnostics. Node and Python implementations agree on all 14
frozen transition vectors and all 77 source-boundary cases, plus two invalid
UTF-8 byte cases. The two resolvers also agree on all 38 package-resolution
inputs. Eleven accepted outputs validate against the closed resolved-ASR schema
and pass identity-closure audits; all six structurally valid identity-tampering
mutations are rejected. The K0 rule index is complete at 69/69, with 26 rules
carrying executable evidence and 43 retaining an explicit evidence gap. Seventy
lexical, package, and structural ASR/Core probes reject later-layer smuggling.

Lean 4 is pinned for mechanized metatheory. Four checked theorem fragments cover
the allocation-cell submodel; none is classified as a full K0 theorem.

See [the generated G0 report](reports/G0.md) for the exact blockers and evidence.

## Repository map

| Path | Purpose |
|---|---|
| `docs/prd/` | Historical product requirements, with v0.3 as the current parent PRD |
| `spec/` | K0 constitution, grammar, ASR/Core contracts, rules, decisions, targets, and conformance corpus |
| `tools/` | Independent Node/Python parsers, package resolvers, transition executors, schema checker, and offline validator |
| `reports/` | Generated G0 status in human- and machine-readable forms |
| `experiment-log.md` | What was tested and learned while the project remains in `lab/` |

Workspace scaffold directories (`inputs/`, `outputs/`, `handoff/`, and `scripts/`)
exist to preserve the enclosing AI-native lab protocol. They are not part of the
language specification.

## Validate

Prerequisites are locked in `spec/manifests/toolchain.json`:

- Node.js `26.4.0`
- Python `3.9.x` at or above `3.9.6` (`3.9.25` in CI)
- Lean `4.24.0` for replay-compatible mechanized proof checks
- Rust/Cargo `1.85.0` to build the independent Nanoda checker
- no external npm or Python packages
- no external Lean packages
- specification validation is offline after host toolchains are present

```sh
npm test
```

Validation parses every JSON artifact, checks Rule ID and test links, runs both
parsers, resolvers, and executors, audits resolved-ASR identities and closure,
rejects layer-boundary mutations, validates closed ASR/Core schemas, verifies
target parameters, rebuilds `spec.lock`, and regenerates the G0 report. A G0
`FAIL` is currently expected; structural or semantic disagreement still makes
the command fail.

Proof fragments use a separate locked toolchain:

```sh
npm run proof:check
```

This builds the proof fragment, replays it with pinned `lean4checker`, exports it
with pinned `lean4export`, and replays the export with the independent Rust
checker `nanoda`, rejecting `sorryAx`. The first run requires network access to
fetch the source trees and Cargo crates at their locked commits and checksums.

## Design discipline

- The implementation is not a source of language semantics.
- A semantic change requires an LCP, an immutable LDR, Rule ID changes,
  conformance evidence, compatibility analysis, and regenerated lock/report.
- K1/K2 features cannot enter the K0 route to make a test pass.
- Tests cannot create semantics; their oracle must cite an existing rule.
- AI output is untrusted until deterministic checks accept it.
